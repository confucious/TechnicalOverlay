# TechnicalOverlay — Agent Instructions

**Platform: iOS (iPhone/iPad).** The app, LayoutEngine (UIKit), and VideoProcessor target iOS.
Build and test against the **iOS simulator** (e.g. `iPhone 17`). The app also runs on
**Apple-silicon Macs as a "Designed for iPad" app** — there is no native macOS target and no Mac
Catalyst (`SUPPORTS_MACCATALYST = NO`).

## Build & Run

The Xcode project is **generated by Tuist** (`Project.swift` at repo root) — the generated
`TechnicalOverlay.xcodeproj`/`.xcworkspace` are gitignored. Regenerate after editing manifests
or adding/removing source files:

```bash
tuist generate
```

Build the app (and the LayoutEngine/VideoProcessor/ProtocolParser frameworks it links) for the
iOS simulator:

```bash
tuist build TechnicalOverlay --device 'iPhone 17' --platform ios
```

Run the app **on this Mac** as a "Designed for iPad" app (Apple silicon). `tuist build` only
targets simulators/devices, so use xcodebuild with the Mac variant of the iOS destination:

```bash
xcodebuild build -scheme TechnicalOverlay -workspace TechnicalOverlay.xcworkspace \
  -destination 'platform=macOS,arch=arm64,variant=Designed for iPad'
```

The capability comes from `.macWithiPadDesign` in `Project.swift`'s `destinations` — Tuist emits
`SUPPORTS_MAC_DESIGNED_FOR_IPHONE_IPAD = YES` (it defaults to **NO**, and without it "My Mac" does
not appear as a run destination at all). Xcode's product destination list shows it as
`My Mac (Designed for iPad)`.

Run tests:

```bash
# All test bundles (no scheme argument — Tuist resolves <Project>-Workspace)
tuist test --device 'iPhone 17' --platform ios

# A single framework's tests
xcodebuild test -scheme LayoutEngine -workspace TechnicalOverlay.xcworkspace \
  -destination 'platform=iOS Simulator,name=iPhone 17'
```

**Two traps, both verified 2026-10-10 (Tuist 4.205):**

1. **`tuist test <FrameworkTarget>` does not run tests.** e.g. `tuist test LayoutEngine` prints
   `The scheme LayoutEngine's test action has no tests to run, finishing early.` and exits 0
   having executed **zero** tests. The test flow focuses the graph on the tested target and
   drops the test bundle before generation, so the scheme's test action is empty. Explicit
   `Scheme` definitions and `--test-targets` / `--no-upload` / `--skip-ui-tests` don't help.
   Use the two commands above instead. `-scheme <Framework>` via xcodebuild works because the
   framework test bundles have no app host.
2. **A `tuist test` run narrows the generated project on disk** to the tested subgraph —
   afterwards `tuist build <X>` fails with `The workspace named TechnicalOverlay does not
   contain a scheme named <X>`, and Xcode opens a gutted project. **Always re-run
   `tuist generate` after a test run.**

**Test health** — every bundle builds and runs on the iPhone 17 simulator. Per-scheme counts, what
each bundle covers and when each was last verified live in [`docs/testing.md`](docs/testing.md) —
**keep them there, not here**: a count written into these instructions goes stale without anyone
noticing, and this file is read on every session.

`VideoProcessorTests` integration tests need the untracked 398 MB
`TechnicalOverlay/TechnicalOverlay/Boston Open 2025.mov`; without it `DefaultStitcherTests`
early-return and pass trivially. They render real chunks and perform real exports, so they are
far slower than the pure-logic suites. The stitcher refuses a plan whose last chunk does not end
exactly at `videoDuration` (defensive; the app always satisfies it by construction), so those
tests pass the plan's own end as the duration.

Two `xcodebuild` reporting traps to know about when reading output:
- `-scheme VideoProcessor` prints its Swift Testing summary and then **hangs in teardown** (0% CPU,
  no `** TEST SUCCEEDED **`). The tests have already passed at that point — kill it or run it
  under a watchdog.
- `-scheme TechnicalOverlay` prints the Swift Testing summary (unit tests) **before** the XCTest
  UI tests run, so that line is not the end of the run.

No lint, no typecheck, no formatter. Swift only; one external package is linked — **SwiftSoup 2.14.2**,
for `ProtocolParser` — and another may be added when it clearly earns its place (policy:
`docs/ARCHITECTURE.md` §2.2). Tests use the **Swift Testing** framework (`@Suite`, `#expect`).

## Tracing the chunk pipeline

`VideoProcessor` traces the chunk pipeline with plain `print` (like the rest of the module),
prefixed by stage, so one export can be followed end to end in Xcode's console:

| Prefix | Reports |
|--------|---------|
| `[ChunkQueue]` | `enqueue` — slides → regions → chunks, how many are new to render vs reused vs newly stale, and a line per non-`noOverlay` chunk with its disposition; drains (start, dequeue, per-chunk outcome with timing, done); `waitForCompletion`; `markStale`; `validChunks` |
| `[ChunkRenderer]` | one chunk being exported: preset compatibility, composition (`constant` overlay / `transition` endpoints + start time), export duration and output size, every failure path |
| `[Stitcher]` | per-chunk assembly (`noOverlay` copies a source range; `constant`/`transition` copy the rendered file, absolute range → local range mapping), composition totals, the passthrough export session |

Chunk ids print as their first 8 UUID characters and ranges as `start–end` seconds
(`12.500–24.000`), so grepping an id (`[ChunkQueue] 51CF6DFC`) correlates a chunk across all
three stages. `ChunkPipelineTrace.swift` holds the shared helpers (`Trace.log`, `TraceTimer`,
`traceDescription`, `traceFileSize`). `print` output only shows when the app runs from Xcode or
a terminal — it does not reach Console.app.

The main interface also shows the queue's state as a dot in the video button row, driven by
`ChunkQueueProgress.isRendering` (reported on enqueue, drain start, after each chunk, and drain
end): **yellow** while any renderable chunk is queued or rendering, **green** once everything is
rendered and the queue is idle, grey when no video is loaded. Chunks left stale by a failed
render don't count as work, so the dot settles instead of sitting yellow forever.

Known artifact in that output: `enqueue` starts a detached drain task and `waitForCompletion`
also calls `drain()`, and `drain()` suspends on each render, so two drains can interleave and
you may see two `drain: done` summaries for one pass. Renders are still serialized (the chunk is
marked `.rendering` before the await), so nothing renders twice.

**Dependencies:** one third-party package is linked — **SwiftSoup 2.14.2**, used by `ProtocolParser` only (pinned exactly in `Project.swift`; `Package.resolved` committed). Everything else is Apple frameworks: SwiftUI, AVFoundation, CoreImage, UIKit, CoreMedia, Observation, UniformTypeIdentifiers. That is the current state, **not a rule**: take a package when it gives an obvious, well-fitted benefit over self-written code (policy and the worked example: `docs/ARCHITECTURE.md` §2.2, `docs/HISTORY.md` → *SwiftSoup adoption*).

**Swift concurrency model — every target is main-actor by default.** `Project.swift`'s
`baseSettings` carries `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` and
`SWIFT_APPROACHABLE_CONCURRENCY = YES`, as the pre-Tuist projects did. Code is therefore
main-actor isolated unless marked `nonisolated` (e.g. `VersionedOverlayData`). **Do not drop these
settings**: without them `generateSlides()`'s `Task` leaves the main actor, `VideoOverlay.render`
then mutates `UILabel` layers from a background thread, and UIKit logs *"Modifying properties of a
view's layer off the main thread is not allowed"*.

**`docs/ARCHITECTURE.md`** is the consolidated spec (module map + data flow + current rules); per-module detail lives in `docs/architecture/`. **Read `docs/ARCHITECTURE.md` before making changes.**

## Documentation

`docs/ARCHITECTURE.md` and `docs/architecture/*.md` carry **current state only** — what the code does
and the rules it has to keep obeying. No dates, no rationale, no measured comparisons, no rejected
alternatives, no bug stories, no "we used to…". All of that lives in **`docs/HISTORY.md`**, which
opens with a chronological decision ledger and then one section per topic.

- **Writing or editing a design doc:** state the rule. Where the reason protects against a plausible
  "simplification", add a one-line directive plus a pointer (`docs/HISTORY.md` → *Playhead freeze*) —
  never the narrative itself. `docs/ARCHITECTURE.md` §2.2 is the worked example for a dependency.
- **Changing a design:** add a row to the ledger and, if the reasoning needs to survive, a dated
  subsection in `HISTORY.md` — in the same change as the doc edit, never later.
- **Test counts, coverage and "verified on <date>"** belong in `docs/testing.md`; never here or in a
  doc.
- **Why:** these docs are read into a session before it can work, so every line of history in them is
  context that gets re-read every time instead of looked up on demand. A stale snapshot in a doc is
  also re-taught instead of corrected — the same reason `AGENTS.md` has no test-count table.

## Data Model — Critical Details

`OverlayData` is marked `@Observable` (Observation framework). Scores are stored as `Int` in **hundredths** (3.40 → 340, -1.19 → -119). All `ElementData` fields (`baseValue`, `goeValue`, `bonusValue`) use this. String ↔ hundredths conversion via `String.toHundredthsInt()` and `ElementData.formatValue()`.

**Cascading timing** — `setIntroTime(index:time:)` and `setElementTime(index:time:)` propagate the delta to all subsequent items, preserving relative spacing. Recursive implementation.

Persistence: `OverlayData.save()`/`load()` writes JSON to UserDefaults under key `"state"`. `.tojson` files are versioned JSON (current version 1) via SwiftUI `FileDocument`.

Two `Metrics` enums exist:
- `VideoProcessor.Metrics.transitionTime = 0.75` — dissolve duration, used in `VideoComposer.setupComposition()` and chunk rendering
- `LayoutEngine.Metrics` — layout constants (`techPaneHeightPercent`, `overlayBorderPercent`, `lowerThirdHeightPercent`, etc.)

## Export Pipeline

Two rendering paths:

1. **VideoComposer** — live preview. `AVVideoComposition` with a render handler that composites slides over source frames in real-time via `CIFilter.dissolveTransition`.

2. **ChunkQueue → DefaultChunkRenderer → DefaultStitcher** — export pipeline. `ChunkQueue.enqueue(slides:)` generates regions, diffs against existing chunks, renders pending ones sequentially. `DefaultStitcher` assembles rendered chunks + source video segments into final output via `AVMutableComposition` track appending.

Export flow in `MainView` — **the destination is chosen before any work happens** (the save panel
is handed a zero-byte `SaveDestinationPlaceholder` and returns the chosen URL), so the passthrough
export writes straight there:
```
fileExporter (pick destination) → waitForCompletion() → stitch(chunks:sourceAsset:videoDuration:to: destination) → ExportSession.performExport()
```
The placeholder file the panel writes at the destination must be deleted before exporting:
`AVAssetExportSession` refuses to write over an existing file. Failures surface as
`ExportPhase.failed(message)` in the progress sheet and clean up the destination file.

Chunk types: `.noOverlay` (source-only, never reused), `.constant` (single CIImage overlay), `.transition` (cross-dissolve between two CIImages).

Chunk diffing (`diffRegionsIntoChunks`) reuses rendered chunks when content identity and time range match — key for incremental updates. `DefaultChunkRenderer` is implemented but the main app export flow uses the chunk queue + stitcher path, not the older `VideoComposer.setupExport()` path.

## Control Flow

```
User loads video (MainView → fileImporter)
    │
    ▼
ViewModel.assetUrl = fileUrl
    │  (startAccessingSecurityScopedResource, generateSlides())
    ▼
generateSlides()
    │  scoring.makeSlides(size:) → VideoOverlay.Mode → VideoOverlay.render() → CIImage → Slide[]
    │  (imageCache keyed by (size, mode) in OverlayData)
    ▼
VideoComposer(asset:slides:) → setupComposition() → AVVideoComposition
    │  AVPlayerItem.videoComposition = composition
    ▼
AVPlayer plays video with overlays composited in real-time

User edits timing (TimeSettingsView)
    │  setIntroTime/setElementTime (cascading)
    │  → generateSlides() → new VideoComposer → replaceCurrentItem
    │  → queue.enqueue(slides:) (re-enqueues for export)

User exports (MainView "Save Video" button)
    │  save panel picks the destination FIRST (zero-byte placeholder document)
    │  queue.waitForCompletion()
    │  DefaultStitcher.stitch(chunks:queue.validChunks(), …, to: destinationURL)
    │  → AVMutableComposition with sequential track inserts
    │  → ExportSession.performExport() writes .mp4 straight to the destination
```

## Gotchas

- The three **chunk-renderer** builders in `VideoComposer` use
  `AVVideoComposition(applyingFiltersTo:applier:)`, whose handler returns
  `AVCIImageFilteringResult(resultImage:ciContext: nil)`. The older
  `videoComposition(with:applyingCIFiltersWithHandler:)` factory is deprecated as of iOS/macOS 27.0.
  A nil image on either side of `setupComposition(from:to:transitionStart:)` means "no overlay on
  that side" (dissolve against `CIImage.clear`) — that is the noOverlay ↔ slide fade.
- `setupComposition()` — the **preview** composition, the only one attached to an `AVPlayerItem` — is
  deliberately *not* one of those: it sets `customVideoCompositorClass` to `PreviewVideoCompositor`,
  our own `AVVideoCompositing`, because the filter API's compositor deadlocks a playhead drag. Do not
  "simplify" it back, and do not share one `AVURLAsset` between the player item and the chunk
  exporter (`docs/HISTORY.md` → *Playhead freeze*).
- `ContentView.swift` is a **legacy prototype** with hardcoded test data. Main entry point is `MainView`.
- `ElementBuilderView.swift` is a **placeholder** — not wired into the app.
- `Metrics.transitionTime = 0.75` in `VideoProcessor` — the dissolve duration, used everywhere in video composition.
- Overlay views render at **1280×720** (hardcoded in `VideoOverlay` init frame).
- Security-scoped URLs: `startAccessingSecurityScopedResource()` / `stopAccessingSecurityScopedResource()` must be paired (see `MainView.ViewModel.assetUrl` setter with `willSet`/`didSet`). Also used in `OverlayDataDocument.read()`.
- `OverlayData` clears its `imageCache` on data changes. Cache is keyed by `(size, mode)`.
- `ScoringListView` saves data and clears cache on `onDisappear`.
- Test bundle identifiers are `org.cjas.jhsu.*` for frameworks, `org.cjas.technical-overlay` for the app.
- `ChunkQueue` is an `actor` — all calls to `render(chunk:)` are serialized. No additional synchronization needed in `DefaultChunkRenderer`.
- `DefaultStitcher` is **not `Sendable`** — `AVAssetReader`/`AVAssetWriter` are not thread-safe.
- The stitcher creates a single `AVMutableComposition` with one video track and one audio track, appending chunks sequentially.
- Export output is `.mov` for chunk rendering, `.mp4` for final stitch.
- `VideoComposer.setupComposition()` (async) returns `AVVideoComposition?` — errors are caught and printed in `generateSlides()`.
- `OverlayData.renderingHash` computes a deterministic hash of all rendering-affecting fields (names, scores, times) — used for cache invalidation decisions.
