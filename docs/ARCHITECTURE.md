## 1. Purpose

An **iOS app** (iPhone/iPad, plus "Designed for iPad" on Apple-silicon Macs) that creates video
overlays for **figure-skating competitions**. It takes a video of a skating performance and overlays
technical scoring information (element names, base values, GOE scores, running **totals**) and
introduction slides, producing a **scored video** with dissolve transitions.

Authoring model: the user loads a video, enters a skater's **introduction slides** and
scoring **elements** (with per-item display timestamps set against a live preview player), and
the app composites the overlays onto the video and exports a new file.

### 1.1 Non-Goals

- Not a camera / recorder (that is the separate InstantReplay **"Retake"** project).
- No live broadcast output — an author-and-burn pipeline producing a finished file.
- No native macOS target (LayoutEngine is UIKit) and no Mac Catalyst.
- No audio manipulation — source audio passes through unchanged.
- No automatic element recognition from the video: elements come from hand entry in the scoring list
  or from a published protocol page (`ProtocolParser` — §2, §7).

### 2.2 Dependencies — current state, and the policy

**State:** the project links **one third-party package** — SwiftSoup 2.14.2 (pinned exactly in
`Project.swift`'s `packages:`, `Package.resolved` committed), used by `ProtocolParser` alone. The
rest is Apple frameworks: SwiftUI, AVFoundation, CoreImage, UIKit, CoreMedia, Observation,
UniformTypeIdentifiers.

**Policy:** use external dependencies **minimally**, and only when one provides an **obvious and
well-fitted benefit over self-written code**. A candidate has to clear all of:

- it removes real work — less code and fewer failure modes than writing it ourselves, not merely
  less typing;
- it is well-fitted — does the job we need (or very nearly) rather than a broader framework we
  would have to work around;
- it is maintained and testable — recent releases, clear licence, and it builds for our actual
  targets (iOS 26 / the simulator / "Designed for iPad");
- its costs are measured, not assumed — build time, linked binary size, transitive footprint
  (a dependency with its own dependency tree is a different decision), and any behaviour it
  imposes on us.

Record the decision, with those measurements, as a row in [`docs/HISTORY.md`](HISTORY.md) and in the
module doc that needs it. The worked example (and the template for how to argue this) is
`docs/HISTORY.md` → *SwiftSoup adoption*.

## 3. Data Model

All data uses Apple's `@Observable` macro (Observation framework). The core model is
`OverlayData` in `OverlayData.swift`:

| Type | Purpose |
|------|---------|
| `OverlayData` | Top-level: `skaterFullName`, `skaterAbbreviatedName`, `introductionTexts: [IntroductionData]`, `elementScores: [ElementData]`. Its `showsElementBox` is the live overlay-look value, seeded from `OverlayPreferences` (not document data). Methods: `save()`/`load()` (UserDefaults), `update(from:)`, `setIntroTime/setElementTime`, `makeSlides(size:)`, `makeSlide(size:mode:startTime:)`, `renderingHash`, `imageCache`, `clearCache()`. |
| `IntroductionData` | One intro slide: `left`/`center`/`right` + optional `displayTime`. `makeMode(skaterName:)` → `.lowerThirdPane`. |
| `ElementData` | One scoring element: `name`, `baseValue`, `goeValue`, `bonusValue` (all `Int` hundredths), optional `displayTime`. String accessors `baseValueString`/`goeValueString`/`bonusValueString` round-trip through `toHundredthsInt()`. `makeMode(skaterName:runningTotal:boxModes:)` → `.technicalPane`. |

### 3.1 Scores are integer hundredths

All score quantities are stored as **`Int` hundredths** (3.40 → `340`, −1.19 → `-119`), **not**
`Double`. Do not reintroduce `Double` for these fields: precision in comparisons and hashing is the
reason. String↔Int conversion lives in a `String` extension (`numberCharacters()`, `onlyDigits()`,
`toHundredthsInt()`), and `ElementData.formatValue(_:decimalPlaces:)` renders `w.ff` with a fixed
fractional width.

### 3.2 Cascading timing

`setIntroTime(index:time:)` / `setElementTime(index:time:)` propagate the delta to all
**subsequent** items of the same kind, preserving relative spacing (recursive implementation).
Unset trailing intro siblings default to `+5s`.

### 3.3 Element colors

Element box color is derived per element: `baseValue == 0` → `.neutral`; `goeValue >= 0` →
`.positive` (green); else `.negative` (red). The running total is the cumulative sum of
`baseValue + goeValue + bonusValue`.

### 3.4 `renderingHash`

`OverlayData.renderingHash` is a deterministic hash of all rendering-affecting fields (names,
scores, times, `showsElementBox`) — used for cache-invalidation decisions in the chunk pipeline.

## 4. Persistence

- **Autosave** — `OverlayData.save()`/`load()` write the whole model as JSON to `UserDefaults`
  under key `"state"`. Saved on every "Start Now" and on `ScoringListView.onDisappear`.
- **File interchange (`.tojson`)** — `OverlayDataDocument` (a SwiftUI `FileDocument`) reads/writes
  **versioned** JSON (`VersionedOverlayData`, `version == 1`) under the custom UTType
  `org.cjas.jhsu.overlay-document` (declared **exported only**, conforming to `public.json`).
  `fileType` is `UTType(exportedAs:)` — never `UTType(filenameExtension:)`, which silently returns
  a **dynamic** type when the extension is unregistered and can't be matched by the file importer.
  The extension is `.tojson`, never `.tod`: `.tod` is claimed by VLC as `public.movie`
  (`org.videolan.tod`), and where that claim owns the tag macOS types our files as a non-conforming
  type and the open panel greys every one of them out (`docs/HISTORY.md` → *Project
  infrastructure*).
  Adding a persisted-model field must bump the version or stay backward-compatible.
- **Device preferences** — `OverlayPreferences` stores overlay-look settings in `UserDefaults`
  (`showsElementBox`, key `"showsElementBox"`, absent = boxes shown). They survive a relaunch and
  apply to every document, so they are **not** in `CodingKeys` and `update(from:)` does not copy
  them: loading a `.tojson` never changes what the device shows.

## 5. Rendering & Composition

### 5.1 Overlay layout — UIKit, proportion-scaled

Overlay graphics are **pure UIKit `UIView` subclasses** in `LayoutEngine`, laid out with
percentage-based metrics so they scale to any output resolution. `VideoOverlay` (base frame
**1280×720**, `alpha = 0.9`, clear background) hosts `IsuTechnicalPaneView` (top-left,
16% height, 2.65 aspect) + `IsuLowerThirdView` (bottom-center, 15% height, 8.5 aspect); its
`Mode` enum (`none | technicalPane | lowerThirdPane`) shows one pane at a time. The technical
pane's element box row is optional (`TechnicalViewModel.showsElementBox`); hiding it moves the name,
score and total rows up by the row's height (`docs/architecture/layout-engine.md` → *Element box row*).

`VideoOverlay.render(size:)` sets bounds, lays out, and rasterizes the `CALayer` to a
`CIImage` via `UIGraphicsImageRenderer` (`scale = 1`, `opaque = false`). Full view hierarchy and
the named `Color`/`Metrics` constants are in `docs/architecture/layout-engine.md`.

### 5.2 Composing onto video — two rendering paths

**`Metrics.transitionTime = 0.75`** (in `VideoProcessor`) is the dissolve duration used
everywhere. `OverlayData.imageCache` caches rendered `CIImage`s keyed by `(size, mode)`;
`clearCache()` empties it on data changes.

**Path 1 — `VideoComposer` (live preview + full-video export).**
`AVVideoComposition` with a per-frame handler that finds the last `Slide` with
`startTime <= compositionTime`, cross-dissolves (0.75s `CIFilter.dissolveTransition`) from the
previous slide, and composites `slide.image.composited(over: request.sourceImage)`. Before the
first slide / for nil slides it passes the source through unchanged. `setupExport` →
`AVAssetExportSession` (highest-quality preset, `.mov`).

**Path 2 — Chunk pipeline (`ChunkQueue` → `DefaultChunkRenderer` → `DefaultStitcher`), wired
into the main app's "Save Video".**
Designed for incremental/reusable rendering:

```
enqueue(slides:, videoDuration:)
  → generateRegions()        → [ChunkRegion]   (contiguous sweep: noOverlay gaps,
                                                 transition windows, constant holds)
  → diffRegionsIntoChunks()  → [Chunk]          (reuse unchanged content, mark rest stale)
  → ChunkQueue.drain()       (actor; dequeue pending → renderer → rendered(URL)/stale)
  → waitForCompletion()      (waits for the drain enqueue() started too — a chunk in the
                              .rendering state is still work, not a chunk that is done)
  → validChunks()
  → DefaultStitcher.stitch() → AVMutableComposition track append → final export
```

- **Chunk types**: `.noOverlay` (source-only, never reused), `.constant(CIImage)` (single
  overlay), `.transition(from, to)` (cross-dissolve). `ContentIdentity` = stable content hash
  independent of time range.
- **Diffing**: `.noOverlay` never reused; `.transition` requires exact time-range match;
  `.constant` may be reused for overlapping portions (splitting new-reuse-new). Unreused
  existing chunks are marked stale (`stitchingTimeRange = nil`).
- **Renderer**: `DefaultChunkRenderer` (implements `ChunkRendererProtocol`) exports each chunk
  as a time-limited `AVAssetExportSession` segment with the appropriate CIImage composition
  (`chunk_<uuid>.mov`). `ChunkQueue` is an actor so `render(chunk:)` calls are serialized.
- **Stitcher**: `DefaultStitcher` (implements `StitcherProtocol`) builds a single
  `AVMutableComposition` with one video + one audio track and appends chunks sequentially,
  mapping absolute stitching ranges to local chunk times (`localTimeRange`) and advancing the
  composition cursor by each **appended range**, never by the source track's own duration. It
  requires the plan to reach `videoDuration` exactly, and returns a
  `VideoComposer.ExportSession` — the file appears only once the caller performs the export. Final
  export is **`.mp4`** via `AVAssetExportPresetPassthrough`.

`MainView.generateSlides()` pre-enqueues slides into the queue so it is ready when the user taps
"Save Video"; the export flow sets `exportPhase` (idle → rendering → stitching → done, or
`failed(message)`) and drives a progress sheet.

Full detail (types, per-chunk composition methods, region/diff algorithms) is in
`docs/architecture/video-processor.md`.

## 6. App Flow

```
Load Video (fileImporter, .movie) → ViewModel.assetUrl
  → startAccessingSecurityScopedResource, generateSlides()
  → makeSlides(size:) (size = naturalSize.applying(transform), abs'ed) → VideoComposer
  → AVPlayerItem.videoComposition → replaceCurrentItem (seek preserves position)
  → chunkQueue.enqueue(slides:) (pre-render for export)

Edit timing (TimeSettingsView "Start Now" → playhead time read at tap time → setIntro/setElementTime,
  cascading) → generateSlides() → new VideoComposer + re-enqueue
  (the timeline is listed whenever there is scoring data; with no video it is read-only, and
  "Start Now" is a hidden placeholder that keeps the row's height)

Jump to a set time (TimeSettingsView's time button → player.seek) — a seek, so no regeneration

Edit overlay look (Element boxes toggle → OverlayPreferences + showsElementBox → generateSlides()
  → new VideoComposer + re-enqueue; changed modes make the diff re-render the affected chunks)

Edit data (ScoringListView → onDisappear save() + clearCache())

Save Video → save panel picks the destination → queue.waitForCompletion()
  → DefaultStitcher.stitch(to: destination)
  → ExportSession.performExport() writes .mp4 straight to the chosen file
```

UI surface (`MainView`): `VideoPlayer` with the **background render indicator** overlaid on its
bottom-right corner, raised by a fixed 72pt inset so it never covers AVKit's control cluster (the
scrubbing control lives in it); it is only on screen while a video is loaded, and it takes no taps
(`allowsHitTesting(false)`). The dot is **yellow while the chunk queue has work queued or
rendering**, **green once every renderable chunk is rendered and the queue is idle** (fed by
`ChunkQueueProgress.isRendering`), with a label on a translucent capsule because the video
underneath is arbitrary. Below the player: `TimeSettingsView` (shown with or without a video;
read-only until one is loaded), a config row holding the
**Element boxes** toggle (hides the technical pane's element box row, persisted in `UserDefaults`,
then regenerates the slides), and a button row
**Load Video | Save Video | Load Slides | Save Slides | Edit Slides** (→ `ScoringListView`
NavigationStack destination). `ContentView.swift` is a **legacy prototype** (hardcoded Scotty HSU
test data) and `ElementBuilderView.swift` is a **placeholder (not wired in)** — the real entry point
is `MainView`.

**Two `AVURLAsset`s over one file, deliberately.** `generateSlides()` builds the player item from
one and hands `DefaultChunkRenderer` a second. Sharing a single instance makes the preview and the
chunk export contend for one asset's decode/compositor state, which freezes the app on a playhead
drag. Do not re-merge them — `docs/HISTORY.md` → *Playhead freeze*.
